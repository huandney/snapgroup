snapgroup por dentro

Um guia em HTML pra abrir no celular e entender, aos poucos, como este projeto Rust liga comandos de terminal, Snapper, Btrfs, rollback e boot. Pensado pra quem está começando em Rust.

Como usar este guia

Leia em camadas. Primeiro o problema. Depois o fluxo dos comandos. Depois conceitos de Rust. Só então os arquivos.

O objetivo não é decorar. É conseguir responder: "quando eu digito um comando, qual arquivo recebe isso, qual função roda e que efeito ela causa no sistema?"

Os blocos <details> abrem com clique. Use-os como uma trilha. Se a explicação ficar fácil, passa adiante. Se travar, abre.

1. Visão Geral

O projeto snapgroup compila num binário chamado snapg. Ele é um wrapper em volta do snapper — ou seja, não substitui o Snapper, só usa o Snapper por baixo e adiciona uma ideia nova em cima: tratar vários snapshots como um único checkpoint lógico.

Exemplo prático. Seu sistema tem dois subvolumes Btrfs: um pra / e outro pra /home. O Snapper normalmente cria um snapshot de cada lado, separadamente. Se você quiser voltar os dois pra um ponto coerente no tempo, tem que correr atrás de dois números diferentes na unha. O snapg resolve isso colocando o mesmo identificador (um timestamp Unix) nos dois snapshots quando você roda snapg save. Pra restaurar, ele acha todos os membros com aquele ID e restaura juntos.

Snapper

Ferramenta externa (já existe no Linux). Cria, lista e apaga snapshots Btrfs. O projeto chama o comando snapper como subprocesso.

Btrfs

Sistema de arquivos que suporta subvolumes e snapshots baratos. O rollback real acontece renomeando subvolumes.

Grupo (checkpoint)

Conjunto de snapshots que compartilham o mesmo snapgroup-id (um timestamp Unix). É o que o save cria.

Regret

O estado anterior à última restauração, guardado como subvolume _snapg_regret. É o botão de arrependimento.

Nota didática — README desatualizado. O README.md ainda descreve comandos antigos: undo, redo e gc. O código atual (em src/cli.rs) usa um conjunto diferente:

  • save — cria checkpoint
  • list — lista checkpoints e mostra regret se existir
  • restore — TUI interativa pra escolher checkpoint ou regret
  • delete — apaga checkpoints (seleção interativa, ou -y pro mais recente)
  • boot-clean — comando interno, escondido, chamado por snapg-cleanup.service no boot

O README precisa ser atualizado. Por enquanto, ignore as referências a undo/redo/gc lá.

2. Conceitos do Domínio

O que é um snapshot?

É uma foto de um subvolume em um momento do tempo. No Btrfs, essa foto não copia todos os arquivos imediatamente — ela compartilha blocos com o estado original e só diverge quando algo muda (copy-on-write).

No projeto, o Snapper cria snapshots read-only (só leitura). Pra restaurar, o snapgroup primeiro tira uma cópia writable (leitura/escrita) desse snapshot e só depois troca pelo sistema vivo.

O que é um subvolume?

Pense num subvolume como uma raiz independente dentro do Btrfs. Em muitos sistemas Arch/CachyOS/openSUSE, / aponta pra @ e /home aponta pra @home.

Top-level Btrfs (subvolid=5)
├── @            -> montado como /
├── @home        -> montado como /home
├── @snapshots   -> snapshots do root
└── @home/.snapshots -> snapshots do home

O detalhe importante: pra trocar @ por outro subvolume, o programa precisa enxergar os subvolumes como irmãos. Isso só é possível olhando o top-level direto. Daí o passo seguinte.

Por que precisa montar o top-level?

O top-level Btrfs (também chamado de subvolid=5) é o "pai" de todos os subvolumes. O snapg monta ele em /run/snapgroup/<uuid> só pelo tempo da operação, faz a troca, e desmonta.

Sem montar o top-level, você não conseguiria fazer mv @ @_backup e mv @_novo @.

Por que o programa pede sudo?

Criar snapshots, montar o top-level, renomear subvolumes e mexer em /boot exigem permissão de administrador. Por isso src/sudo.rs reexecuta o próprio binário com sudo quando você roda como usuário comum.

Olhe esse trecho de src/sudo.rs:

let err = Command::new("sudo").args(&args).exec();

O .exec() substitui o processo atual em vez de criar um filho. Resultado: você só vê um processo, sem PID extra.

3. Rust Básico para iniciantes

Esta seção é um glossário. Cada item explica um conceito de Rust com a forma mais simples possível, e mostra onde ele aparece neste projeto. Volte aqui sempre que cruzar um conceito desconhecido.

fn — função

Uma função é um bloco de código com nome que faz uma tarefa. Você chama pelo nome e ela executa.

fn epoch_now() -> Result<i64> {
    // ... gera um número baseado no tempo atual
}

fn declara função. epoch_now é o nome. -> Result<i64> diz "retorna um Result que, quando dá certo, tem um i64 dentro".

let — variável

Variável em Rust é criada com let. Por padrão, ela é imutável (não muda depois de criada).

let id = epoch_now()?;         // imutável
let mut buf = String::new();   // mutável (pode mudar)

Para permitir modificação, você adiciona mut. Essa diferença força você a pensar antes em "isso vai mudar mesmo?".

struct — pacote de dados

Uma struct agrupa dados relacionados. É como criar um tipo novo composto por campos.

pub struct Group {
    pub id: GroupId,
    pub members: Vec<Member>,
}

Aqui um Group tem dois campos: um id e uma lista (Vec) de membros. pub significa "público" — outros módulos podem usar.

enum — uma escolha entre opções

Um enum diz: "este valor é uma destas variantes". Em src/cli.rs:

pub enum Command {
    Save { description: Option<String> },
    Restore,
    List,
    Delete { yes: bool },
    BootClean,
}

Um Command é exatamente um desses cinco. Você não pode ter dois ao mesmo tempo. Cada variante pode carregar dados próprios — Save carrega uma descrição opcional, Delete carrega o flag -y.

match — escolha pelo formato do dado

O match olha um valor e escolhe o que fazer pra cada variante. O compilador exige cobrir todas as possibilidades — se você esquecer uma, o código não compila.

match cli.command {
    Command::Save { description } => commands::save(description),
    Command::Restore              => commands::restore(),
    Command::List                 => commands::list(),
    Command::Delete { yes }       => commands::delete(yes),
    Command::BootClean            => commands::boot_clean(),
}

Essa exaustividade é uma das coisas que tornam Rust seguro: se amanhã você adicionar um comando novo no enum, o compilador apita em todos os match que ficaram incompletos.

Option<T> — pode ter valor, pode não ter

Rust não tem null. Quando algo pode existir ou não, o tipo é Option<T>. Ele tem duas variantes:

  • Some(valor) — tem valor
  • None — não tem
description: Option<String>

Lê-se: "uma String que pode ou não estar presente". Pra usar, você precisa abrir com match, if let Some(...) ou .unwrap_or(...).

Result<T, E> — pode dar certo, pode falhar

Muitas funções aqui retornam Result<()> ou Result<Vec<Group>>. Significa: ou devolve o valor esperado (Ok(...)), ou devolve um erro (Err(...)).

pub fn list_groups() -> Result<Vec<Group>> {
    // se tudo der certo: Ok(groups)
    // se algo falhar:     Err(...)
}

O projeto usa o crate anyhow, que carrega mensagens de erro com contexto encadeado ("falhou em X: por causa de Y: por causa de Z").

? — propaga erro pra cima

Quando você vê algo()?, leia assim: "execute algo; se falhar, pare esta função e devolva o erro pra quem me chamou".

let configs = snapper::list_configs()?;

Se list_configs() retornar Err, a função atual também retorna Err imediatamente. Isso evita escrever if/else manual pra cada erro.

Vec<T> — lista dinâmica

Vec é uma lista que cresce. Equivalente ao list de Python ou ArrayList de Java.

let mut created = Vec::new();      // lista vazia
created.push((cfg.clone(), n));    // adiciona item
for (cfg, n) in &created { ... }   // itera
& e &mut — referência (borrow)

Quando você vê &configs ou &mut buf, isso é uma referência ao dado. Significa: "estou emprestando esse valor, não vou levar pra sempre".

fn delete_existing_regrets(toplevel: &Path, configs: &[String]) -> Result<()>

O &Path diz "empresta um path, só vou ler". O &[String] diz "empresta uma fatia de Strings". Isso evita cópias desnecessárias e impede que duas partes do código mexam no mesmo dado ao mesmo tempo de forma confusa.

Resumo iniciante: & = "vou só olhar". &mut = "vou olhar e modificar". Sem & = "estou levando o dado comigo (move)".

mod — módulo

Um módulo é uma forma de organizar código em arquivos/namespaces. No topo de src/main.rs:

mod boot;
mod btrfs;
mod cli;
mod commands;
mod group;
mod rollback;
mod snapper;
mod sudo;

Cada mod nome; aqui diz "existe um arquivo src/nome.rs que faz parte deste programa". Daí em diante você usa funções com nome::funcao().

crate — biblioteca externa (ou seu próprio projeto)

Um crate é a unidade de compilação em Rust. Pode ser o seu projeto inteiro (binário ou lib) ou uma dependência externa. Este projeto usa estes crates externos:

  • clap — parser de argumentos de linha de comando
  • anyhow — erros com contexto encadeado
  • serde e serde_json — converter JSON do Snapper em structs Rust
  • dialoguer e console — menus interativos no terminal (TUI)

Você os declara em Cargo.toml e o cargo baixa.

Comando externo (Command::new)

O projeto não reimplementa Snapper nem Btrfs. Ele chama os comandos do sistema como se você os tivesse digitado no terminal:

let out = Command::new("snapper")
    .args(["--jsonout", "list-configs"])
    .output()?;

Isso cria um processo filho que roda snapper --jsonout list-configs, espera ele terminar, e te dá um Output com três coisas: o código de saída, o stdout e o stderr.

stdout e stderr

Todo programa Unix tem três fluxos:

  • stdin (entrada padrão) — o que você digita
  • stdout (saída padrão) — texto normal de resultado. No projeto, é onde vai a saída útil: lista de configs, JSON, número do snapshot criado
  • stderr (saída de erro padrão) — mensagens de erro e avisos

Veja como o projeto separa os dois:

if !out.status.success() {
    bail!(
        "snapper list-configs: {}",
        String::from_utf8_lossy(&out.stderr)   // erro do subprocesso → erro nosso
    );
}
let parsed = serde_json::from_slice(&out.stdout)?;  // saída útil → parse JSON

Princípio: println! escreve em stdout, eprintln! escreve em stderr.

4. Arquitetura do Projeto

O programa segue uma cadeia linear simples. Toda chamada começa em main e desce:

Terminal
  ↓
$ snapg save "antes de atualizar"
  ↓
src/main.rs         (parseia argumentos, garante sudo, despacha)
  ↓
src/cli.rs          (define quais comandos existem — usado por main)
  ↓
src/sudo.rs         (se não for root, reexecuta com sudo)
  ↓
src/commands.rs     (orquestra: aqui mora a lógica de alto nível)
  ↓
src/snapper.rs      ─┐
src/group.rs         │  fazem o trabalho concreto
src/btrfs.rs         │
src/rollback.rs      │
src/boot.rs         ─┘

A camada commands é o coração. É ela que conhece todos os outros módulos e os encaixa em um fluxo. Os módulos mais baixos (snapper, btrfs, boot) não conhecem uns aos outros — só sabem chamar comandos externos.

5. Fluxo dos Comandos

snapg save "descrição"

1
Gera um ID.
Em commands::save, a função epoch_now() devolve um número baseado no tempo Unix atual. Esse número vira o snapgroup-id do grupo.
2
Lista configs Snapper.
snapper::list_configs() chama snapper --jsonout list-configs e devolve algo como ["root", "home"].
3
Mata regret antigo (regra Highlander).
kill_regrets() monta o top-level e apaga qualquer *_snapg_regret que exista. Um novo save significa "estou aceitando a linha do tempo atual; não preciso mais voltar".
4
Cria os snapshots.
Para cada config, snapper::create() chama snapper -c <cfg> create --userdata snapgroup-id=<id>. Todos compartilham o mesmo ID.

snapg list

Lista os grupos existentes. O trabalho principal é em group::list_groups(): ele varre todos os snapshots de todas as configs, lê o snapgroup-id de cada um, e agrupa os que compartilham o mesmo ID em um Group. Ordena do mais recente pro mais antigo. Por fim, commands::list ainda chama show_regret_status() pra avisar se existe um regret ativo.

snapg restore

1
Carrega checkpoints e monta top-level.
group::list_groups() + btrfs::mount_toplevel().
2
Procura regret.
discover_regrets() verifica se existe um *_snapg_regret no top-level. Se sim, vira a primeira opção do menu.
3
Mostra menu TUI.
dialoguer::Select renderiza a lista. Use setas e Enter.
4
Executa.
Se você escolheu checkpoint → execute_restore_checkpoint() chama rollback::rollback_group(). Se escolheu regret → execute_restore_regret() chama rollback::revert_regret().
5
Sincroniza /boot se for FAT32.
Se /boot está em vfat (legado), boot::sync_fat32() copia o vmlinuz novo, regenera initramfs e atualiza hashes do Limine.
6
Pergunta se quer reiniciar.
prompt_reboot() roda systemctl reboot -i (o -i ignora inhibitors da sessão gráfica).

snapg delete

Sem -y: usa dialoguer::MultiSelect pra você marcar quais checkpoints apagar (com Espaço). Com -y: apaga só o mais recente, sem perguntar — mantido por compatibilidade com scripts.

snapg boot-clean interno

Comando escondido (#[command(hide = true)] em cli.rs). É invocado pelo snapg-cleanup.service no boot seguinte a uma restauração de regret. Ele:

  1. Monta o top-level.
  2. Procura subvolumes com nome *_snapg_discard_* (sobras da restauração de regret — eram o sistema vivo antes do swap).
  3. Apaga cada um.
  4. Roda systemctl disable snapg-cleanup.service pra se desarmar.

6. Rust no Projeto (em contexto)

Vimos os conceitos isolados na seção 3. Aqui vamos ver os mesmos conceitos aparecendo juntos, no código real.

Como o argumento da linha de comando vira código

O crate clap faz a tradução. Você descreve um struct/enum com derive macros e ele monta o parser:

// src/cli.rs
#[derive(Subcommand)]
pub enum Command {
    Save { description: Option<String> },
    Restore,
    List,
    Delete { #[arg(short = 'y', long)] yes: bool },
    #[command(hide = true)]
    BootClean,
}

Depois, em main.rs:

let cli = cli::Cli::parse();    // lê argv, devolve o enum preenchido
match cli.command { ... }       // despacha por variante

Tudo conectado por tipos: o que o usuário digita vira um valor de um enum tipado.

Como JSON do Snapper vira struct

Em src/snapper.rs:

#[derive(Debug, Deserialize)]
pub struct Snapshot {
    pub number: u32,
    #[serde(rename = "type")]
    pub kind: String,
    pub date: String,
    pub user: String,
    pub description: String,
    pub cleanup: String,
    pub userdata: Option<serde_json::Value>,
}

O #[derive(Deserialize)] diz ao serde: "ensine como ler isso de JSON". O #[serde(rename = "type")] resolve o conflito com a palavra reservada type em Rust.

O parse acontece em uma linha:

let parsed: serde_json::Value = serde_json::from_slice(&out.stdout)?;
Como o projeto chama um comando externo com segurança

Padrão repetido em todo lugar:

let out = Command::new("snapper")
    .args(["-c", config, "create", "--description", description])
    .output()
    .context("snapper create falhou")?;       // erro de I/O? aborta com contexto

if !out.status.success() {                    // saiu com código != 0?
    bail!(
        "snapper create -c {config}: {}",
        String::from_utf8_lossy(&out.stderr)
    );
}

Três checagens em cada chamada: (1) o I/O da chamada não falhou? (2) o processo terminou com sucesso? (3) o stdout faz sentido pra parse?

Como erros sobem de uma função fundo até a TUI

Cadeia típica num snapg save:

main()                       Result<()>
  ↓
commands::save()             Result<()>
  ↓
snapper::list_configs()?     Result<Vec<String>>
  ↓
Command::new("snapper").output()?

Cada ? é uma "tomada de saída". Se um nível abaixo der erro, a função atual sai com Err imediatamente. O anyhow mantém a corrente: você lê erros como "falhou ao criar snapshot em 'home': snapper create -c home: ENOSPC".

7. Arquivo por Arquivo

Arquivo Responsabilidade Quem chama Funções principais
main.rs Ponto de entrada. Parseia argumentos, garante root, despacha. kernel/shell main()
cli.rs Define os comandos aceitos via clap. main Cli, Command
sudo.rs Se não é root, reexecuta com sudo. main ensure_root(), current_uid()
commands.rs Orquestra os comandos. É o "regente" que conhece todos os outros módulos. main save, restore, list, delete, boot_clean
snapper.rs Ponte com o comando externo snapper (cria/lista/apaga snapshots, lê configs). commands, group list_configs, list, create, delete, config_subvolume
group.rs Transforma snapshots soltos em grupos pelo snapgroup-id. commands extract_id, list_groups
btrfs.rs Ponte com btrfs, mount, findmnt, date. Operações de subvolume. commands, rollback mount_toplevel, create_snapshot, delete_subvolume, subvol_relative_path, fs_uuid, now_local_label
rollback.rs A parte mais delicada: prepara, troca e desfaz subvolumes em duas fases. commands rollback_group, revert_partial, revert_regret, delete_existing_regrets, regret_name
boot.rs Caso especial: /boot em FAT32. Copia kernel, regenera initramfs, atualiza hashes Limine. commands is_fat32, sync_fat32, refresh_limine_boot_hashes

A conexão que importa

main.rs
  chama cli.rs       (entender o que foi digitado)
  chama sudo.rs      (virar root se preciso)
  chama commands.rs  (executar)

commands.rs
  chama snapper.rs   (falar com Snapper)
  chama group.rs     (juntar snapshots em checkpoints)
  chama btrfs.rs     (montar top-level, mexer em subvolumes)
  chama rollback.rs  (trocar subvolumes com segurança)
  chama boot.rs      (sincronizar /boot FAT32, se for o caso)

Veja que rollback.rs também chama btrfs.rs e snapper.rs, mas não chama commands.rs. A dependência só desce — nunca sobe. Isso é desenhado de propósito: módulos baixos não conhecem a UI, só fazem o trabalho.

8. Pontos Perigosos

Este programa mexe em rollback do sistema

Erros em rollback.rs, btrfs.rs ou boot.rs podem deixar o sistema exigindo recuperação manual via live USB. Qualquer mudança aqui deve ser testada em VM antes.

rollback.rs é o centro de risco

A função rollback_group() tem duas fases bem definidas:

Fase 1 — Preparação. Cria cópias writable dos snapshots em nomes intermediários (@.snapgroup_prep, @home.snapgroup_prep). Operação cara (metadata copy), pode falhar por falta de espaço. Se falhar aqui, o sistema vivo ainda não foi tocado. O programa apaga os preps e aborta limpo.

Fase 2 — Commit. Renomeia os subvolumes: @ → @_snapg_regret, depois @.snapgroup_prep → @. Renames são metadata-only e atômicos por syscall. Quase nunca falham. Se falhar no meio de um grupo, o programa pergunta se você quer reverter automaticamente.

Mount sobrevive ao rename — por quê?

O kernel Linux referencia mounts por inode, não por path. Quando você faz mv @ @_snapg_regret com @ montado como /, o mount continua válido — você ainda está rodando dentro do mesmo subvolume, ele só mudou de nome no top-level.

A troca real só vale no próximo boot, quando o fstab/initramfs vai procurar @ e encontrar o subvolume novo. Daí o prompt_reboot() no fim.

.snapshots aninhado precisa ser preservado

No layout padrão, /.snapshots e /home/.snapshots são subvolumes filhos dentro de @ e @home. Quando você renomeia @ pra @_snapg_regret, o .snapshots vai junto. O código então move .snapshots de volta pro novo @ ativo. Veja commit_prep() em rollback.rs, etapa 3.

/boot em FAT32 é caso especial

Se /boot está fora do Btrfs (FAT32 / vfat), ele não volta automaticamente com o snapshot. Kernel e initramfs no /boot podem corresponder a uma versão diferente do sistema que você acabou de restaurar.

Por isso boot::sync_fat32():

  1. Descobre a versão do kernel dentro do snapshot restaurado (/usr/lib/modules/<kver>/vmlinuz).
  2. Faz backup dos arquivos atuais de /boot.
  3. Copia o vmlinuz do snapshot pra /boot.
  4. Regenera o initramfs usando mkinitcpio -r <snapshot> -c <snapshot>/etc/mkinitcpio.conf.
  5. Atualiza os hashes BLAKE2B no /boot/limine.conf pra refletir os arquivos novos.

Se qualquer passo falhar, o backup de /boot é restaurado.

"Regra Highlander": só existe um regret

O regret é único por design. Toda vez que você faz um novo save ou restore, o regret anterior é deletado (kill_regrets / delete_existing_regrets).

Razão: regrets ocupam espaço (são cópias writable). Se acumulassem, o disco entupiria. E semanticamente, "estado anterior à última restauração" só faz sentido se for um único estado.

9. Roteiro de Estudo

Use esta ordem pra estudar sem se perder:

1
Leia src/main.rs.
É pequeno (23 linhas). Mostra a ideia central: parsear, garantir sudo, despachar via match.
2
Leia src/cli.rs.
Veja como o argumento de terminal vira um enum.
3
Leia src/snapper.rs.
O padrão "comando externo + parse de saída" se repete em todo lugar. Aqui ele aparece limpo.
4
Leia src/group.rs.
Curto e cristalino. Veja como o snapgroup-id transforma snapshots soltos em checkpoint.
5
Leia src/commands.rs::save.
Fluxo mais simples do commands: descobrir configs, matar regret, criar snapshots.
6
Leia src/btrfs.rs.
Mais comandos externos, agora envolvendo Btrfs. Funções pequenas e independentes.
7
Só depois leia src/rollback.rs.
Esse arquivo exige entender Btrfs, subvolumes e o motivo da troca por renomeação. Leia já com a ideia das duas fases na cabeça.
8
Por último, src/boot.rs.
Caso especial (FAT32). Pode ficar pra depois se você não tem /boot em vfat.

Exercício 1 — Siga o snapg list com o dedo

Abra src/main.rs e siga o comando até o fim:

main()
  → match Command::List
  → commands::list()
  → group::list_groups()
  → para cada config:
      snapper::list_configs()
      snapper::list(config)
      group::extract_id(snapshot)
  → agrupa por snapgroup-id
  → ordena (mais recente primeiro)
  → imprime
  → show_regret_status() (monta toplevel, procura regret)

Se você consegue explicar esse caminho em voz alta, já entendeu a espinha dorsal do projeto.

Exercício 2 — Identifique todos os comandos externos

Procure por Command::new( no projeto (com grep -rn 'Command::new(' src/) e liste quais binários externos o snapg usa. Você deve achar pelo menos: snapper, btrfs, mount, umount, findmnt, date, uname, mkinitcpio, b2sum, systemctl, sudo.

O projeto inteiro é uma orquestração desses binários, com lógica Rust no meio.

Exercício 3 — Quebre o match

Imagine que você adicionou uma variante nova no enum Command, ex: Status. O que o compilador vai reclamar? Onde? Por que isso é uma boa coisa?

Esse é o tipo de garantia que faz Rust não te deixar esquecer de tratar um caso. Aproveite.
